# Output Structure Review

**Date:** 2026-06-02
**Method:** Full code review of all index/viewer builders and runners; cross-checked against QA session output from batch fixture runs. Analysis only — no code changed.

---

## Executive Summary

The current output structure is **sound in intent but has two concrete problems and one UX inefficiency:**

1. **No `viewer.html` exists anywhere.** The concern was unfounded. The viewer is always `viewer.htm`.
2. **`index.htm` / `index.html` duplicates** exist at the municipality and scrape-entry levels. They are identical in content. The duplication is intentional as a browser-compatibility alias but creates confusion about which file is canonical.
3. **One extra click** separates the user from the viewer on complete (OK) runs. The scrape entry page (`Municipality/date/index.html`) is a pure pass-through for successful runs — it only says "Archive ready. Open viewer." For error/partial runs it carries real information, so it should be retained only for those.
4. **One mislabeled back-link:** the municipality index labels its global back-link as "← Run index" but points to the global index, not the run index.
5. **Dead legacy code** in `AppRunner.LegacyRunAsync` and `Program.LegacyRunAsync` contains a `TryBuildViewerAsync` that omits the output filename parameter, causing the viewer to be written as `index.htm` (overwriting the entry page) in error/cancel cases. This code is unreachable, but it is a latent correctness trap if the routing ever changes.

## Current Generated Structure

Every production run via `ProductionRunner.RunAsync` writes these files:

```
output/
  index.htm                          ← GlobalIndexBuilder: all runs, links to EntryRel
  _cli_temp.log                      ← transient CLI log (not part of archive)
  _runs/
    yyyy-MM-dd_HHmmss/
      run.log                        ← human-readable run log
      run.json                       ← run manifest (all sites, status, counts)
      {host}.log                     ← per-site structured log
      index.htm                      ← TopIndexBuilder: this run's site list
  Municipality/
    index.htm                        ← MunicipalityIndexBuilder: all dated runs
    index.html                       ← MunicipalityIndexBuilder: DUPLICATE of index.htm
    index.json                       ← machine-readable run metadata list
    yyMMdd/
      index.htm                      ← SiteRunArtifacts: scrape entry page
      index.html                     ← SiteRunArtifacts: DUPLICATE of index.htm
      viewer.htm                     ← SiteViewerBuilder: the actual archive viewer
      nav.json                       ← navigation index
      scrape.json                    ← scrape metadata (status, counts, EntryRel, ViewerRel)
      pages/
        p_*.htm                      ← extracted text HTML per page
        p_*.text.htm                 ← cleaned text variant
      shots/
        p_*.full.webp                ← full-page screenshot (short pages)
        p_*.tile000N.webp            ← tile sequence (tall pages)
```

**No `viewer.html` is generated anywhere.** `SiteViewerBuilder.BuildAsync` accepts an `outputFileName` parameter with a default of `"index.htm"`, but every active call site passes `"viewer.htm"` explicitly.

## Current Click Path

There are two forward paths from the global index to the viewer:

### Path A — Via run index (3 clicks)
```
output/index.htm
  → (click run title) → _runs/runId/index.htm
    → (click municipality name) → Municipality/date/index.html
      → (click "Open viewer") → Municipality/date/viewer.htm
```

### Path B — Direct municipality link (2 clicks)
```
output/index.htm
  → (click municipality name under run) → Municipality/date/index.html
    → (click "Open viewer") → Municipality/date/viewer.htm
```

The global index renders each run with:
- A run title that links to the run index (Path A entry)
- A list of municipalities under that run that link **directly to the scrape entry page** (Path B, using `EntryRel`)

So the minimum from global index to viewer is **2 clicks**, not 3. The 3-click path exists via the run index — useful when navigating between sites in the same run.

### Back-navigation

```
viewer.htm
  → (🏠 home button: ../../index.htm) → output/index.htm

Municipality/date/index.htm
  → (← Municipality index: ../index.htm) → Municipality/index.htm
  → (All runs: ../../index.htm) → output/index.htm

Municipality/index.htm
  → (← Run index: ../index.htm) → output/index.htm   ⚠️ LABEL IS WRONG
```

## Redundant or Confusing Files

### 1. `index.html` / `index.htm` duplicates (municipality + scrape level)

Both files are written with identical content in the same write operation. The comment in `MunicipalityIndexBuilder.cs` line 129 explicitly says "Backward compatible" for the `.htm` copy.

The naming inversion makes this confusing:
- The builder treats `.html` as the primary output and `.htm` as the alias
- But all higher-level indexes and back-links reference `.htm` (e.g., `../index.htm`)
- The `scrape.json` `EntryRel` field stores `.html`, so the global index links use `.html`
- Both exist, both work — but there is no consistent canonical extension

**Verdict:** Redundant but harmless. The `.htm` form is what all navigation links actually use. The `.html` form is what `scrape.json:EntryRel` stores (and thus what the global index links use). Keeping both ensures everything resolves regardless of which extension is referenced.

### 2. `viewer.html` — does not exist

No code path generates `viewer.html`. This concern can be dismissed.

### 3. The scrape entry page for complete runs

`Municipality/date/index.htm` (and `.html`) is a one-link page for OK runs: "Archive ready. Open viewer." It adds one mandatory click on the happy path with no informational value. For error/partial/cancelled runs it shows status, reason, and note — genuinely useful.

**Verdict:** Useful for non-OK runs. Unnecessary click for OK runs.

### 4. Mislabeled municipality index back-link

`MunicipalityIndexBuilder.cs` writes:
```html
<div class="sub"><a href="../index.htm">← Run index</a></div>
```
From `output/Municipality/index.htm`, `../index.htm` resolves to `output/index.htm` — the **global index**, not the run index. The run index lives at `output/_runs/runId/index.htm` and is not directly back-linkable from the municipality index (there can be multiple runs). The label is misleading.

**Verdict:** Label bug. Should read "← All archives" or "← Global index".

### 5. Dead legacy code with a latent viewer-overwrites-entry bug

`AppRunner.LegacyRunAsync` (line 304) and `Program.LegacyRunAsync` (line 431) both contain:
```csharp
await viewer.BuildAsync(siteDir, host, startUrl); // no filename → defaults to "index.htm"
```
This would overwrite the scrape entry page with the viewer HTML in error/cancel cases. These methods are unreachable — `AppRunner.RunAsync` and `Program.RunAsync` both delegate to `ProductionRunner.RunAsync`. But if the routing were ever reverted, the bug would silently corrupt scrape entry pages.

**Verdict:** Dead code, latent bug. Safe to delete.

- All index-level and back-links use `.htm` exclusively

- There is no broken link in the current system

**Stale folders:** When a site is retried on the same day, an empty `yyMMdd` folder is created before the run is redirected to `yyMMdd_2`. These empty folders are unreferenced (no links point to them, no `scrape.json` inside). They appear as dead clutter in the municipality directory.

## Recommended Product Structure

### Comparison of options

| Option | Description | Clicks (OK run) | Complexity |
|---|---|---|---|
| **A (current)** | Global → (run index) → Scrape entry → Viewer | 2–3 | No change |
| **B** | Global links directly to scrape entry; municipality index for history | 2 (same as current) | No change |
| **C** | Global links directly to viewer for OK runs; scrape entry for non-OK | 1 | Minor code change in GlobalIndexBuilder + TopIndexBuilder |
| **D** | Remove duplicate .html/.htm aliases | 2–3 | Minor code change in MunicipalityIndexBuilder + SiteRunArtifacts |
| **C+D** | Both: direct viewer link for OK + single extension | 1 | Two minor changes |

### Recommendation: **Option C for links, Option D deferred**

**Implement Option C:** When status is `OK`, the global index and run index should link directly to `viewer.htm#start` instead of the scrape entry page. When status is anything other than `OK` (PARTIAL, ERROR, CANCELLED, CAP_REACHED), link to the entry page so users see the status and reason.

This requires:
- `GlobalIndexBuilder.cs`: when building the municipality `viewerHref`, prefer `ViewerRel` when status is OK, otherwise use `EntryRel`
- `TopIndexBuilder.cs`: same logic in `LinkFor` / `BuildAsync`

Both builders already have access to the `Status` field.

**Defer Option D (alias cleanup):** The `.htm`/`.html` duplication is harmless and removing one alias risks breaking any external links or tools that may reference the non-canonical form. Defer until there is a specific reason.

**Fix the mislabeled back-link** in `MunicipalityIndexBuilder.cs`: change "← Run index" to "← All archives".

**Delete the dead legacy code** in `AppRunner.cs` and `Program.cs` to eliminate the latent viewer-overwrites-entry bug.

## What Not To Change Yet

- **The municipality index layer.** It provides genuine value: historical navigation across multiple dated runs for the same municipality. It is the right place to browse if you want to compare two runs. Even though it is only reachable via back-link today, it should be retained.
- **The scrape entry page for non-OK runs.** It is the only place that surfaces status, reason, and note for partial/failed/cancelled scrapes. Essential for operators reviewing a bad run.
- **The `pages/` text HTML files.** The viewer iframe loads these directly. Removing or restructuring them would break the viewer.
- **The `.html` aliases.** Defer removal until the canonical extension is settled and all link-generation code is updated atomically.

## Final Answers

**Q: Is `viewer.html`/`viewer.htm` redundant?**
No — there is only `viewer.htm`. No `viewer.html` exists anywhere in the code or output. The viewer is a single file.

**Q: Does the user path have too many clicks?**
Marginally. The minimum is 2 clicks (global → scrape entry → viewer), which is acceptable. The scrape entry adds a click with no information for successful runs. One code change in `GlobalIndexBuilder` and `TopIndexBuilder` eliminates this for OK runs, reducing the path to 1 click.

**Q: What is the safest improvement?**
Fix the mislabeled back-link in `MunicipalityIndexBuilder` (zero risk, instant clarity) and update the global/run indexes to link directly to `viewer.htm` when status is OK (low risk, removes the unnecessary pass-through click on the happy path). Both are isolated, additive changes that do not touch the viewer, the crawl pipeline, or the output structure.
